# Labelit 2026 Q2 OKR 브레인스토밍 문서

---

## 전략 맥락

| 전략 축 | 핵심 과제 | 비즈니스 임팩트 |
|---------|-----------|----------------|
| **Gen2 Feature 개발** | Gen1 대비 향상된 레이블링 기능 설계 및 출시 | 신규 고객 확보 및 기존 고객 업셀 기회 창출 |
| **Gen1 → Gen2 통합** | Gen1 Feature를 Gen2 아키텍처에 흡수·병합 | 유지보수 비용 절감, 사용자 경험 일원화 |
| **Gen2 로그 포맷 수집** | Gen2 전용 로그 스키마 정의 및 파이프라인 구축 | 데이터 기반 의사결정 기반 마련 |
| **검증 프로세스 구축** | 로그 품질 보증 및 자동화된 QA 체계 수립 | 데이터 신뢰도 확보, 모델 학습 품질 향상 |

> **Q2 전략 방향 요약:** Gen2로의 전환을 가속화하면서, Gen1 자산을 손실 없이 흡수하고, 데이터 수집·검증 인프라를 동시에 완성한다. 세 축이 유기적으로 연결되어야 Gen2 플랫폼의 완전성이 확보된다.

---

## OKR Set A — Gen2 플랫폼 완성도 집중 전략

> *"Gen2를 선택할 이유를 만든다 — Feature 완성이 곧 전환의 트리거다"*

| 구분 | 내용 |
|------|------|
| **Objective** | Gen2 Feature를 Gen1 대비 기능적으로 동등하거나 초월한 수준으로 완성하여, 사용자가 Gen2로 자발적으로 전환하도록 만든다 |
| **KR 1** | Gen1에서 활성 사용 중인 Feature 목록 대비 Gen2 지원율을 Q2 말까지 **60% → 90%** 로 끌어올린다 (미지원 Feature 수: 현재 N개 → 잔여 N×0.1개 이하) |
| **KR 2** | Gen2 신규 Feature 3개 이상을 **사용자 테스트 → 피드백 반영 → 정식 릴리즈** 사이클로 완료하며, 각 Feature의 태스크 완료율(Task Completion Rate) **80% 이상** 달성 |
| **KR 3** | Gen2를 주 워크플로우로 사용하는 활성 사용자 비율을 **전체 MAU의 40% 이상**으로 끌어올린다 (현재 기준 측정 후 목표 설정) |

**전략적 근거:**
Gen2 전환의 가장 큰 병목은 "Gen1에서 쓰던 기능이 Gen2에 없다"는 Feature Gap 문제입니다. OKR Set A는 이 Gap을 Q2 내에 극적으로 좁혀서, 사용자가 전환을 미루는 기술적·심리적 이유를 제거하는 데 집중합니다. KR 1은 기능 완성도 지표, KR 2는 신규 기능의 UX 품질, KR 3은 실제 전환 행동을 각각 측정하여 Output과 Outcome을 균형 있게 추적합니다.

## OKR Set B — Gen1·Gen2 통합 및 기술 부채 청산 전략

> *"두 개의 세계를 하나로 — 통합이 완성되는 순간, 유지보수 비용이 사라진다"*

| 구분 | 내용 |
|------|------|
| **Objective** | Gen1 Feature의 Gen2 통합을 체계적으로 완료하여, 단일 코드베이스 기반의 지속 가능한 제품 운영 구조를 만든다 |
| **KR 1** | Gen1 Feature 통합 대상 목록(Migration Backlog)을 Q2 1주차까지 **100% 인벤토리화**하고, 우선순위·의존성·공수 추정을 완료한다 (미정의 항목 0건) |
| **KR 2** | Migration Backlog 중 **Critical/High 등급 Feature의 80% 이상**을 Gen2에 통합 완료하며, 통합 후 회귀 테스트(Regression Test) 통과율 **95% 이상** 유지 |
| **KR 3** | Gen1 전용으로만 유지되던 코드 모듈 수를 **현재 대비 50% 이상 감소**시키고, 이를 통해 CI/CD 빌드 시간을 **20% 단축**한다 |

**전략적 근거:**
Gen1과 Gen2를 병렬 운영하는 상황은 엔지니어링 리소스를 이중으로 소모하고 버그 수정의 복잡도를 높입니다. OKR Set B는 통합 작업을 전략적 우선순위로 격상시켜, Q2 말까지 "Gen1 종속성 절반 제거"라는 가시적 성과를 내는 전략입니다. KR 1의 인벤토리화는 모든 통합 작업의 선행 조건이며, KR 3의 빌드 시간 단축은 통합의 실질적 효과를 개발팀이 체감할 수 있는 지표로 설정했습니다.

## OKR Set C — Gen2 데이터 인프라 및 신뢰성 구축 전략

> *"보이지 않는 기반을 완성한다 — 좋은 로그가 좋은 모델을 만든다"*

| 구분 | 내용 |
|------|------|
| **Objective** | Gen2 로그 포맷 수집 및 검증 프로세스를 완전히 구축하여, 레이블 데이터의 품질과 추적 가능성을 보장하는 인프라를 완성한다 |
| **KR 1** | Gen2 전용 로그 스키마(이벤트 타입, 필드 정의, 버전 관리 체계 포함)를 Q2 3주차까지 **확정·문서화**하고, 전체 Gen2 Feature의 **100%**에 로그 이벤트를 심는다 |
| **KR 2** | 로그 수집 파이프라인의 **데이터 유실률 0.1% 이하**, 수집 지연(latency) **평균 5초 이내**를 달성하고, 이를 실시간 모니터링 대시보드로 가시화한다 |
| **KR 3** | 로그 품질 자동 검증 프로세스(스키마 유효성 검사, 이상치 탐지, 누락 이벤트 알람)를 구축하여, **일 배치 기준 검증 커버리지 90% 이상** 및 이상 탐지 후 **알람 발송까지 10분 이내** 달성 |

**전략적 근거:**
Gen2 로그 인프라는 제품 개선과 ML 모델 학습 모두에 영향을 미치는 크리티컬 기반입니다. 로그가 없거나 신뢰할 수 없으면, 이후의 모든 데이터 기반 의사결정이 흔들립니다. OKR Set C는 "수집(KR 1) → 안정적 전달(KR 2) → 품질 보증(KR 3)"의 3단계를 Q2 내에 완성하는 전략입니다. 특히 KR 3의 자동 검증은 운영 팀의 수동 QA 부담을 줄이고, 데이터 이슈를 실시간으로 감지할 수 있는 자율 운영 체계를 목표로 합니다.

## 권장 선택 가이드

| 팀 상황 | 추천 OKR | 이유 |
|---------|----------|------|
| **Gen2 전환율이 정체되어 있고, 사용자 이탈 신호가 포착된 경우** | **Set A** | 사용자가 Gen2를 선택하지 않는 근본 원인인 Feature Gap을 해소하는 것이 최우선 |
| **엔지니어링 팀의 유지보수 부담이 크고, 두 버전 병렬 운영으로 개발 속도가 저하된 경우** | **Set B** | 기술 부채 해소가 장기 속도를 결정하므로, Q2를 통합 집중 분기로 설정하는 것이 전략적 |
| **데이터 품질 이슈로 의사결정 신뢰도가 낮거나, ML 모델 학습 데이터 확보가 급한 경우** | **Set C** | 로그 인프라 없이는 이후 모든 개선 루프가 작동하지 않으므로 선행 투자 필요 |
| **Feature 개발 + 통합을 동시에 추진해야 하는 중간 규모 팀** | **Set A + Set B 혼합** | KR 우선순위를 조정하여 Feature 완성도(A-KR1,2)와 Critical 통합(B-KR1,2)을 병행 |
| **데이터/인프라 팀과 제품 팀이 분리되어 독립 실행이 가능한 경우** | **Set A + Set C 병행** | 제품팀은 Set A, 데이터팀은 Set C를 독립 트랙으로 운영하여 Q2 내 두 성과 동시 달성 |
| **Q2가 Gen2 런칭 직전 분기인 경우 (모든 것을 완성해야 하는 경우)** | **Set A → B → C 순서로 스프린트 배분** | 사용자 가치(A) → 기술 안정성(B) → 데이터 기반(C) 순으로 의존성 방향에 맞게 실행 |

## 부록: OKR 실행을 위한 Q2 마일스톤 제안

```
Week 1-2  : Gen1 Feature 인벤토리 완성 + Gen2 로그 스키마 확정
Week 3-4  : Critical Migration 착수 + 로그 수집 파이프라인 MVP 배포
Week 5-8  : Gen2 신규 Feature 개발·테스트 + 통합 Feature 회귀 테스트
Week 9-10 : 로그 검증 자동화 완성 + 사용자 전환율 중간 점검
Week 11-12: Gen2 활성 사용자 캠페인 + Q2 OKR 최종 측정 및 회고
```

> **⚠️ 리스크 주의사항**
> - Gen1/Gen2 통합 중 예상치 못한 의존성 발견 시 일정 버퍼 20% 확보 권장
> - 로그 스키마는 한번 배포 후 변경 비용이 크므로, Week 1-2 내 이해관계자 승인 필수
> - KR 수치는 현재 베이스라인 측정 후 팀 합의로 최종 조정할 것
