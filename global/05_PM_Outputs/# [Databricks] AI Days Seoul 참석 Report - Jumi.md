# Databricks AI Day Seoul 참석 보고서

## 1. 보고 목적
이번 보고서는 Databricks AI Day Seoul에서 들은 내용을 바탕으로, Databricks를 `데이터 변환을 담당하는 엔지니어`, `대시보드와 지표를 운영하는 분석가`, `현업 사용자가 데이터를 활용하도록 돕는 담당자` 입장에서 어떻게 활용할 수 있을지를 정리하기 위해 작성하였습니다.
특히 현재 Nova에서 진행 중인 Databricks PoC, Lakehouse 고도화, MLflow/DVC 구축, Delivery.xlsx 자동화, 대시보드 이관 검토와 연결하여, Databricks가 실제 일하는 방식에 어떤 변화를 줄 수 있는지에 초점을 두었습니다.

## 2. 이번 행사에서 본 Databricks의 의미
이번 행사에서 느낀 Databricks의 핵심 가치는 “새로운 저장소”보다는 `변환`, `분석`, `대시보드`, `자연어 질의`, `Agent 활용`이 한 플랫폼 안에서 이어진다는 점에 있었습니다.
분석가나 엔지니어 입장에서 보면, Databricks의 의미는 다음과 같이 정리할 수 있습니다.
* 데이터 변환 담당자에게는 `dbt 모델과 배치 스케줄 중심의 흐름이 Databricks Job / Workflow 중심으로 재편될 수 있는 플랫폼`
* 대시보드 담당자에게는 `같은 데이터, 같은 SQL, 같은 권한 체계 안에서 Dashboard까지 이어지는 분석 소비 플랫폼`
* 현업 지원 담당자에게는 `Genie와 Agent를 통해 많은 사용자가 더 쉽게 데이터 자산에 접근할 수 있게 해주는 플랫폼`
즉, Databricks를 도입한다는 것은 단순히 툴 하나를 더 쓰는 것이 아니라, 데이터 자산을 `더 빨리 만들고`, `더 쉽게 보여주고`, `더 넓게 쓰이게 하는 방식`으로 바꾸는 일에 가깝다고 생각합니다.

## 3. 현재 담당 업무 관점에서 본 Databricks 활용 방향

### 3.1 데이터 변환 관점: dbt 모델 중심 경험이 Databricks Job 중심 운영으로 이동할 수 있습니다
현재 담당 업무 관점에서 가장 먼저 와 닿는 부분은 `데이터 변환 방식의 변화`입니다.
기존에는 dbt 모델, SQL 스크립트, 별도 스케줄러, 개별 점검 로직이 나뉘어 있었다면, Databricks에서는 이 흐름이 `Job`, `Workflow`, `Notebook`, `SQL`, `품질 체크`, `모니터링`으로 한 플랫폼 안에 묶일 수 있습니다.
이 변화는 단순히 실행 위치가 바뀐다는 의미보다, 실제 작업 방식이 다음처럼 달라진다는 점에서 의미가 있습니다.
* Bronze → Silver → Gold 변환 흐름을 Databricks Job 기준으로 더 명확하게 운영할 수 있습니다.
* SQL 기반 변환과 Python 기반 처리를 같은 런타임 안에서 관리할 수 있습니다.
* 데이터 적재, 정제, 품질 체크, 스케줄, 실패 확인까지 같은 화면에서 이어서 볼 수 있습니다.
* “모델을 만들고 끝”이 아니라 “언제 실패했는지, 누가 고쳐야 하는지, 다음 단계에 어떤 영향이 있는지”까지 더 쉽게 따라갈 수 있습니다.
현재 Nova에서 `dbt > Job`으로 운영 중심이 바뀌는 흐름을 체감하고 있다면, Databricks의 가치는 바로 이 지점에서 가장 크게 느껴질 수 있습니다.
즉, Databricks는 변환 로직 자체를 마법처럼 바꿔주는 도구라기보다, `변환 작업을 운영 가능한 형태로 더 일관되게 묶어주는 플랫폼`으로 볼 수 있습니다.

### 3.2 대시보드 관점: 데이터 변환 결과와 소비 화면 사이의 거리를 줄여줍니다
대시보드 담당자 입장에서 중요한 것은 어떤 BI 툴이 더 예쁘고 직관성이 좋은지, 지표를 만들고 수정하고 설명하는 과정이 얼마나 짧아지는 지 입니다.
이번 행사에서 본 Databricks의 강점은 Dashboard 자체보다, `DBSQL`, `semantic layer`, `Genie`, `AI Functions`와 대시보드가 같은 맥락 안에서 연결된다는 점이었습니다.
이 관점에서 Databricks를 쓰게 되면 다음과 같은 장점이 있습니다.
* 변환에 사용한 Gold 데이터와 Dashboard가 같은 플랫폼에 있으므로 수정 반영 속도가 빨라집니다.
* 대시보드와 SQL이 더 가까워져서, 지표 정의 변경 시 커뮤니케이션 비용이 줄어듭니다.
* 동일한 KPI를 Dashboard와 Genie가 함께 사용하도록 만들 수 있습니다.
* 대시보드 사용자가 “왜 이 수치가 나왔는가”를 SQL/설명/질의 형태로 더 쉽게 따라갈 수 있습니다.
현재 Superset을 계속 사용할지 Databricks Dashboard로 갈지 고민 중이라면, 그 판단 기준도 기능 비교만으로는 부족하다고 생각합니다.
실제로는 아래 질문이 더 중요합니다.
* 지표 수정과 배포가 어느 쪽이 더 빠른가
* 대시보드 담당자가 데이터 변환 결과와 더 가깝게 일할 수 있는가
* 권한, 메타데이터, 정의서, 자연어 질의까지 한 흐름으로 연결할 수 있는가
* 현업 사용자가 단순 조회를 넘어 “질문”까지 할 수 있는가
즉, 대시보드 관점에서 Databricks는 단순 대체재가 아니라, `대시보드를 분석 소비의 끝이 아니라 시작점으로 바꾸는 도구`가 될 수 있습니다.

### 3.3 Genie 관점: 많은 사용자가 자산을 더 쉽게 쓰게 만드는 접점입니다
이번 행사에서 가장 실무적으로 크게 느껴진 부분은 Genie였습니다.
분석가나 엔지니어가 시간을 많이 쓰는 일 중 하나는, 사실 데이터를 직접 만드는 것뿐 아니라 “이 숫자가 뭐냐”, “어떻게 봐야 하냐”, “이건 어디서 보냐”를 반복 설명하는 일입니다.
Genie는 이 반복 업무를 줄여줄 수 있는 가능성이 있었습니다.
* 현업 사용자가 SQL을 몰라도 자연어로 질문할 수 있습니다.
* 자주 받는 질문을 Dashboard 외에도 질의형으로 받을 수 있습니다.
* 담당자가 직접 쿼리를 대신 짜주지 않아도 되는 구간이 생깁니다.
* Gold mart와 metric 정의가 실제 사용으로 연결되기 쉬워집니다.
다만, Genie는 그냥 켠다고 잘 되는 기능은 아닙니다.
정확히 쓰이기 위해서는 다음이 먼저 정리되어야 합니다.
* 핵심 테이블 범위
* 컬럼 설명
* 동의어
* business 용어 정의
* 자주 묻는 질문 패턴
* benchmark 질문 세트
즉, Genie는 단순한 챗봇이 아니라 `잘 정리된 데이터 자산을 많은 사람이 쉽게 접근하게 만드는 입구`라고 보는 것이 맞습니다.

### 3.4 Agent 관점: Dashboard와 Genie를 넘어서 “자산 활용 보조자”를 만들 수 있습니다
고성능 Genie 세션과 Agent 관련 발표에서 인상적이었던 부분은, Genie 하나로 끝나는 것이 아니라 여러 분석 자산을 연결해 `역할을 가진 Agent`로 확장할 수 있다는 점이었습니다.
이 부분은 저희가 가진 자산에도 충분히 연결 가능합니다. 예를 들어 다음과 같은 형태를 생각해볼 수 있습니다.
* `정산 확인 Agent`: 라벨링 정산 데이터, object 수, delivery 일정 기준으로 주요 수치 설명
* `딜리버리 모니터링 Agent`: 지연 가능성, 주차별 물량 변화, 프로젝트별 상태 요약
* `대시보드 안내 Agent`: 어떤 대시보드를 봐야 하는지, 지표 정의가 무엇인지 안내
* `데이터 FAQ Agent`: object_count, object, 전달일 등 자주 묻는 질문에 대한 답변 제공
결국 Agent의 의미는 “AI를 도입한다”가 아니라, `분석가와 엔지니어가 반복해서 하던 설명 업무를 구조화해서 자산 접근성을 높인다`는 데 있다고 생각합니다.

## 4. 현재 Nova 데이터와 연결했을 때 실무적으로 기대되는 변화
현재 저희가 직접 다루고 있는 `business` 데이터는 라벨링 정산, `object`, `object_count`, 딜리버리 일자, 알고팀 전달 관련 정보를 담고 있습니다.
이 데이터는 Databricks의 활용 가능성을 보여주기에 좋은 예시입니다.

### 4.1 데이터 변환
현재 기준으로 보면 다음과 같은 흐름이 Databricks Job 중심으로 더 일관되게 운영될 수 있습니다.
* Delivery.xlsx 적재
* 정산 원천 데이터 정리
* object / object_count 집계
* 전달일 기준 리드타임 계산
* 프로젝트/고객사 기준 Gold mart 생성
* 품질 체크 및 실패 모니터링
즉, “파일 적재”, “정제”, “집계”, “검증”, “배치 운영”이 분산된 작업이 아니라 하나의 운영 흐름처럼 보일 수 있습니다.

### 4.2 대시보드
이 데이터로는 현 대시보드 외의 다음과 같은 Dashboard 활용이 가능합니다.
* 프로젝트별 object_count 추이
* 객체 유형별 물량 및 단가 비교
* 주차별 물량 변화와 이상치 확인
중요한 것은 Dashboard가 결과 화면으로만 끝나는 것이 아니라, 이후 Genie와 연결되어 “왜 이런 결과가 나왔는지”까지 질문할 수 있는 구조를 만들 수 있다는 점입니다.

### 4.3 Genie/Agent
이 데이터 위에서 Genie 또는 Agent가 유용하게 쓰일 수 있는 질문은 다음과 같습니다.
* 지난달 정산액이 가장 큰 프로젝트는 무엇입니까
* object_count 대비 단가가 높은 작업은 무엇입니까
* 최근 4주 동안 딜리버리 지연이 많았던 프로젝트는 어디입니까
* 알고팀 전달까지 가장 오래 걸리는 유형은 무엇입니까
* 이번 주에 확인이 필요한 이상치가 있습니까
이런 질문을 사람이 매번 직접 받아서 SQL로 답하는 대신, Genie와 Agent가 일정 부분 대신하게 되면 데이터 자산의 활용 범위가 넓어질 수 있습니다.

## 5. 시사점

### 5.1 TMAP: 어려운 것은 도입보다 “운영 전환”입니다
TMAP 사례는 Databricks를 도입하는 순간보다, 기존 테이블과 잡, 워크플로우, 사용자 기대치를 어떻게 옮길지가 더 어렵다는 점을 보여주었습니다.
이 점은 현재 저희가 겪고 있는 `dbt에서 Job으로 중심이 이동하는 경험`과도 맞닿아 있습니다. 

### 5.2 분석은 SQL처럼, 인사이트는 AI처럼: 분석가의 업무를 직접 줄여주는 방향입니다
이 세션은 AI Functions와 Genie가 결국 분석가의 일을 대체한다기보다, `SQL로 만들던 자산을 더 많은 사람이 쉽게 쓰도록 만들어 준다`는 점에서 의미가 컸습니다.
즉, 분석가가 만든 결과물이 더 넓게 사용되게 해주는 방향입니다.

### 5.3 고성능 Genie 세션: Genie의 성패는 준비된 데이터 자산에 달려 있습니다
이 세션은 Genie 품질이 모델 성능보다 `시맨틱 정리`, `핵심 테이블 선정`, `동의어`, `질문 세트`, `예제 SQL`에 달려 있다는 점을 매우 실무적으로 보여주었습니다.
이는 곧, 잘 만들어 둔 자산이 있어야 Genie도 잘 작동한다는 뜻입니다.

### 5.4 LG U+: Agent와 검색형 서비스는 가능하지만 운영 설계가 중요합니다
LG U+ 사례는 LLM 서비스가 가능하다는 점보다, 운영 피로도와 벤더 의존성을 함께 고민해야 한다는 점을 잘 보여주었습니다.
따라서 저희도 Agent를 만든다면 “재미있는 데모”보다 “반복 업무를 실제로 줄일 수 있는가”를 기준으로 접근해야 합니다.

### 5.5 DATA DYNAMICS: 변환/대시보드와 별개가 아니라 운영까지 이어져야 합니다
이상탐지와 성능 관리 사례는 모델 운영 이야기처럼 보이지만, 실제로는 `한 번 만든 결과를 계속 신뢰할 수 있게 관리하는 방식`이라는 점에서 변환과 대시보드 운영에도 같은 교훈을 줍니다.
데이터 품질, 모니터링, 이력 관리가 같이 가야 실제 자산 활용이 확장됩니다.

## 6. 정리

### 6.1 데이터를 만드는 일이 더 연결됩니다
변환 로직, 스케줄, 품질 체크, 실패 대응이 끊겨 있지 않고 더 한 흐름으로 관리됩니다.

### 6.2 만든 결과를 보여주는 일이 더 가까워집니다
Gold mart를 만들고, SQL로 검증하고, Dashboard를 만들고, 정의를 설명하는 과정이 더 짧아집니다.

### 6.3 많은 사용자가 우리 자산을 더 쉽게 쓰게 됩니다
Dashboard는 보는 창구가 되고, Genie는 질문하는 창구가 되며, Agent는 반복 설명을 대신하는 창구가 될 수 있습니다.

## 7. 결론
이번 Databricks AI Day Seoul을 통해 가장 크게 느낀 점은, Databricks가 인프라 관리 뿐만 아니라,`데이터를 만드는 사람`, `대시보드를 운영하는 사람`, `사용자 질문을 받아주는 사람`의 일도 연결해주는 도구라는 점이었습니다.
현재 저희 입장에서 Databricks의 가장 현실적인 가치는 다음과 같습니다.
* 데이터 변환은 `dbt/분산 배치 경험`에서 `Job 중심 운영 경험`으로 더 일관되게 바뀔 수 있습니다.

* Agent를 활용하면 더 많은 사용자가 저희 데이터 자산을 쉽게 접근하고 이용할 수 있게 만들 수 있습니다.
