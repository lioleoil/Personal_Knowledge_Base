# Nova Platform — 2026 Q2 OKR 브레인스토밍

> **작성 목적:** 2026 Q2 전략 방향(유저 활성화 / 아키텍처 전환)을 기반으로 팀이 선택 가능한 OKR 후보군을 도출하고, 각 안의 전략적 근거와 트레이드오프를 명확히 한다.

---

## 전략 맥락

| 전략 축 | 핵심 과제 | 비즈니스 임팩트 |
|---|---|---|
| 🟢 유저 활성화 | Help Center 개발을 통해 신규 유저의 온보딩 마찰을 줄이고, 기존 유저의 기능 활용도를 높인다 | 이탈률 감소 → LTV 향상 / 지원 비용 절감 / NPS 개선 |
| 🔵 아키텍처 전환 | 레거시 데이터 파이프라인을 Databricks 기반으로 전환하여 데이터 처리 속도·확장성·비용 효율을 확보한다 | 인프라 운영 비용 절감 / 신기능 출시 속도 향상 / 데이터 신뢰도 제고 |

> **Q2 전략적 긴장:** 두 축은 리소스(엔지니어링 bandwidth)를 공유하므로, 팀 규모와 성숙도에 따라 집중 또는 병행 전략을 선택해야 한다.

---

## OKR Set A — 유저 활성화 집중형

> *"유저가 Nova를 처음 켠 순간부터 '아, 이거다' 라고 느낄 때까지의 거리를 최소화한다"*

| 구분 | 내용 |
|---|---|
| **Objective** | Help Center를 핵심 성장 레버로 확립하여, Nova 유저가 스스로 성공 경험을 만들어가는 플랫폼을 구축한다 |
| **KR 1** | Help Center 론칭 후 6주 내, 신규 가입 유저의 **7일 리텐션율을 현재 대비 +20%p** 달성 (예: 35% → 55%) |
| **KR 2** | Help Center 콘텐츠 충족률(검색 후 이탈 없이 문서 도달) **75% 이상** 달성 — 최소 핵심 기능 Top 10 커버리지 완료 |
| **KR 3** | Help Center 도입으로 CS 티켓 중 **'기능 사용법' 카테고리 인입 건수를 30% 감소**시키고, 평균 티켓 해결 시간을 48h → 24h 이하로 단축 |

**전략적 근거:**
- 일반적으로 SaaS 제품의 이탈 원인 1위는 "어떻게 써야 할지 모르겠다"는 온보딩 실패이며, Help Center는 이를 가장 낮은 비용으로 해결하는 수단
- KR 1은 비즈니스 성과(리텐션), KR 2는 제품 품질(콘텐츠 완성도), KR 3은 운영 효율(CS 부담 경감)로 3개 차원을 균형 있게 커버
- Databricks 전환은 Q3로 이월하여 Q2는 유저 가치 창출에 집중하는 **순차 전략**

**트레이드오프:** 아키텍처 기술 부채가 누적될 수 있으며, 데이터 처리 병목이 존재하는 상태에서 유저 증가 시 성능 리스크 발생 가능

## OKR Set B — 아키텍처 전환 집중형

> *"흔들리지 않는 기반 위에서만 빠르게 달릴 수 있다 — Q2는 Nova의 엔진을 교체하는 분기다"*

| 구분 | 내용 |
|---|---|
| **Objective** | Databricks 기반 데이터 아키텍처로의 전환을 완료하여, Nova의 데이터 처리 신뢰도와 개발 생산성을 근본적으로 향상시킨다 |
| **KR 1** | 레거시 파이프라인 대비 **데이터 처리 지연시간(P95 latency)을 60% 단축** (예: 4시간 배치 → 90분 이하) |
| **KR 2** | Databricks 전환 완료 모듈 비율 **전체 파이프라인의 80% 이상** 달성 (마이그레이션 체크리스트 기준), 데이터 정합성 오류율 0.1% 미만 유지 |
| **KR 3** | 신규 데이터 피처 개발 사이클을 현재 평균 **3주 → 1.5주 이하**로 단축 (엔지니어 설문 기반 측정 + 실제 피처 배포 건수 비교) |

**전략적 근거:**
- Databricks 전환이 지연될수록 신기능 개발 속도가 발목 잡히고, 데이터 신뢰성 이슈로 인한 내부 의사결정 비용 증가
- 아키텍처 전환은 집중적인 엔지니어링 시간이 필요하므로 "반만 전환"은 오히려 복잡도를 높이는 위험이 있음 → Q2 내 단기 집중이 효율적
- KR 3의 개발 사이클 단축은 Q3 이후 유저 활성화 피처를 빠르게 출시하는 선행 조건

**트레이드오프:** Q2 내 유저 대면 기능 개선이 제한되므로, 외부(고객·투자자)에게 "이번 분기 성과"를 설명하기 어려울 수 있음. 내부 정렬 필수

## OKR Set C — 유저 활성화 + 아키텍처 병행형 (균형 전략)

> *"겉은 유저를 위해, 속은 미래를 위해 — Nova는 Q2에 두 개의 심장을 동시에 강화한다"*

| 구분 | 내용 |
|---|---|
| **Objective** | Help Center로 유저 자립도를 높이는 동시에, Databricks 전환으로 플랫폼 데이터 신뢰도의 기반을 확보한다 |
| **KR 1** | Help Center 오픈 후 **월간 활성 유저(MAU) 대비 Help Center 이용률 40% 이상** 달성, 이용 유저의 기능 활용 지표(Feature Adoption Rate) +15%p |
| **KR 2** | Databricks 파이프라인 전환율 **핵심 모듈(Critical Path) 기준 100% 완료**, 전체 파이프라인 기준 50% 이상 마이그레이션 |
| **KR 3** | 두 전략의 교차 성과: Help Center 콘텐츠 기반 데이터(검색어, 이탈 페이지)를 Databricks 파이프라인으로 분석하여, **콘텐츠 개선 사이클을 2주 단위로 운영** (Q2 내 최소 3회 iteration 완료) |

**전략적 근거:**
- KR 3이 두 전략 축의 시너지를 만드는 핵심: Help Center의 사용 데이터를 Databricks로 분석 → 콘텐츠 품질 루프를 가속화
- 리소스가 분산되는 위험을 KR 2에서 "Critical Path 100%" 조건으로 제어 — 핵심만 먼저 전환하고 나머지는 Q3로 이월
- 병행 전략은 외부 커뮤니케이션(유저 가치 + 기술 역량 동시 어필)에 유리

**트레이드오프:** 두 OKR 모두 중간 수준 달성에 그칠 위험(focus 분산). 팀 규모가 10명 미만이라면 실행력 저하 가능성 높음. **스쿼드 분리(Help Center 팀 / Infra 팀)가 전제되어야 현실적**

## 권장 선택 가이드

| 팀 상황 | 추천 OKR | 이유 |
|---|---|---|
| 이탈률이 임계치(예: 30일 리텐션 < 40%)를 넘어서 즉각적인 유저 성과가 필요한 경우 | **Set A** | 단기 비즈니스 임팩트 극대화, 외부 설명 용이 |
| 데이터 파이프라인 장애·지연이 주 1회 이상 발생하고 엔지니어 번아웃이 가시화된 경우 | **Set B** | 기술 부채 방치 시 Q3 이후 더 큰 비용 발생 |
| 팀 규모 15명 이상, 스쿼드 분리 운영 가능하고 두 방향 모두 스테이크홀더 압박이 있는 경우 | **Set C** | 병행 가능 조건 충족 시 시너지 효과 최대화 |
| 투자 유치 또는 엔터프라이즈 계약을 Q3에 앞두고 있어 제품 데모·안정성이 중요한 경우 | **Set B → Set A 순차** | 아키텍처 안정화 후 유저 경험 강화가 데모에서 더 강한 인상 |
| 유저 인터뷰에서 "기능을 어떻게 써야 하는지 모르겠다"는 피드백이 반복되는 경우 | **Set A 또는 Set C** | 명확한 유저 니즈 시그널 → Help Center 우선순위 상향 |

## 부록 — OKR 실행을 위한 선행 체크리스트

```
✅ Help Center 관련
- [ ] 현재 CS 티켓 카테고리 분류 데이터 존재 여부 확인
- [ ] 기준 7일 리텐션 수치 정의 및 측정 방법 합의
- [ ] Help Center 콘텐츠 오너십 (PM? CS? 테크라이터?) 결정

✅ Databricks 전환 관련
- [ ] 현재 파이프라인 전체 목록 및 Critical Path 정의 완료 여부
- [ ] P95 latency 현재 baseline 측정값 확보
- [ ] 마이그레이션 완료 기준(Definition of Done) 엔지니어링 팀 합의

✅ 공통
- [ ] Q2 엔지니어링 capacity 확인 (두 전략 병행 가능한지 수치 검토)
- [ ] OKR 리뷰 케이던스 설정 (격주 체크인 권장)
- [ ] 각 KR의 측정 도구·대시보드 Q2 시작 전 준비 완료
```
