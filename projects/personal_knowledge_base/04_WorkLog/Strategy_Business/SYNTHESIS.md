# Strategy_Business 위키 합성 문서

## 핵심 지식

1. **KPI는 달성 여부를 판별할 수 있는 수치여야 한다** — "단순 수치화를 위한 숫자"와 "의미 있는 측정 지표"를 구분해야 한다. Goal이 명확하지 않으면 Metric은 장식에 불과하다. (대화 [8], [12])

2. **OKR Key Result는 KPI에서 역으로 도출 가능하다** — 예: `D+1 → 실시간 전환`, `MongoDB 정합성 95% → 99.9%` 두 KPI를 묶으면 "인프라 개선 및 자동화" OKR의 Key Result가 된다. KPI → KR 전환 시 상위 목표(Objective)와의 정합성이 핵심이다. (대화 [27])

3. **Policy·문서 자산의 Git 기반 거버넌스 전환이 측정 대상이 된다** — `전체 Policy 중 Git Markdown 구조 전환 비율`처럼, 운영 프로세스의 디지털 전환 자체를 KPI로 설정하는 방식이 실제 사용되고 있다. (대화 [8])

4. **Nova Lakehouse의 데이터 거버넌스는 ODD 데이터의 규명·정의·통제 체계를 포함한다** — 단순 수집 플랫폼이 아니라, 데이터의 의미와 기준을 정하는 의사결정 프레임이다. "거버넌스"라는 명칭은 성립하되, 범위를 좁히는 보완 명칭(예: ODD Data Governance)을 붙이는 것이 정확하다. (대화 [22], [19])

5. **기술 전환 표현은 맥락에 따라 용어를 선택해야 한다** — `Databricks Query Engine Migration`(로드맵·문서용), `workload` 대신 `capacity`, `task volume`, `throughput` 등으로 대체하는 방식이 실제 업무 문서에서 활용된다. (대화 [28], [30])

6. **Nova의 전략적 방향은 데이터 이동에서 의미(Meaning) 관리로 전환 중이다** — AI가 파이프라인 생성을 자동화하는 환경에서, 데이터 엔지니어링의 핵심 가치는 구조적 자산화와 의미 기반 거버넌스로 이동하고 있다. (대화 [9])

## 반복 등장 패턴

- **KPI/OKR 작성 요청이 반복됨** — 단순 작성 요청이 아니라 "이 지표가 의미 있는가"를 스스로 검토하는 방식으로 질문이 고도화되고 있음 (대화 [8], [12], [27])
- **영어 표현 변환 요청이 잦음** — 로드맵·문서·슬랙 등 실무 작성 맥락에서 정확한 뉘앙스의 영어 표현을 요구함 (`workload`, `migration`, `assigned to a project` 등) (대화 [18], [28], [30])
- **Nova / Nova Lakehouse 관련 개념 정리가 반복됨** — 거버넌스, 데이터 파이프라인, ODD, KPI 등 Nova 프로젝트 전반의 개념을 지속적으로 정의하고 구조화하는 흐름 (대화 [9], [22], [27])
- **용어의 정확한 정의 요청** — `ingestion`, `데이터 거버넌스`, `레이크하우스`, `스키마 vs 테이블` 등 기술 용어를 혼용 없이 정확히 구분하려는 패턴 (대화 [14], [19], [20], [26])
