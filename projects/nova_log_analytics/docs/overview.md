# Labelit Command Log Pipeline — 과업 개요

## 목적

Labelit 라벨링 워크스페이스에서 발생하는 커맨드 로그를 **데이터 신뢰성이 확인된 자산**으로 적재하여, 분석 가능한 환경을 제공한다.

단순한 로그 수집이 아니라, 수집된 데이터가 **정의된 구조를 충족하고 있음을 검증한 뒤 분석 레이어에 공급**하는 것이 이 과업의 핵심이다.

---

## 배경

Labelit은 라벨링 작업자(라벨러)가 3D 오브젝트를 조작하는 워크스페이스를 제공한다. 라벨러가 수행하는 모든 커맨드(오브젝트 선택, 이동, 취소 등)는 CloudEvents 1.0 형식으로 발행되며, 이 로그를 기반으로 다음과 같은 분석이 가능하다.

- 라벨러의 오브젝트 선택 행동 패턴
- 3D bbox 이동 거리 및 빈도
- 작업 취소(undo) 패턴
- 피처별 행동 비교

이 분석을 신뢰성 있게 수행하려면, 로그가 **정의된 구조대로 수집·파싱·적재되었음**이 보장되어야 한다.

---

## 목표하는 결과

```
데이터 신뢰성이 확인된 로그 데이터를 자산으로서 적재하여
분석 가능한 환경을 제공한다.
```

구체적으로:

| # | 목표 | 달성 기준 |
|---|------|-----------|
| 1 | 커맨드 이벤트 원본 보존 | Raw 레이어에 CloudEvent JSON 원본 1:1 미러링 |
| 2 | 분석 가능한 형태로 파싱 | Staging 레이어에서 JSON을 컬럼 단위로 파싱 완료 |
| 3 | 비즈니스 로직 적용 | Intermediate 레이어에서 is_reverted, 3D 이동 거리 등 계산 |
| 4 | 데이터 신뢰성 검증 | 완전성(C1~C5) + 품질(Q1~Q4) 검증이 정기적으로 PASS |
| 5 | 신규 커맨드 도달 확인 | 등록된 모든 커맨드가 Spot Check를 통해 수집 완료 확인 |

## 핵심 컨셉

### 1. 신뢰성 우선 적재

로그를 무조건 수집하는 것이 아니라, **정의된 커맨드만 정해진 구조로** 수집한다.
- 수집 대상 커맨드와 구조는 App Engineer가 스펙으로 정의
- 파이프라인은 스펙 기반으로 파싱하며, 미정의 커맨드는 별도 처리
- 신규 커맨드는 Spot Check를 통해 도달 확인 후 정기 검증으로 이관

### 2. 레이어 분리로 책임 명확화

| 레이어 | 역할 | 변경 정책 |
|--------|------|-----------|
| **Raw** | 원본 보존 (파싱 없음) | 증분 MERGE — 원본 훼손 없음 |
| **Staging** | JSON 파싱, 세대 분류 | 증분 INSERT |
| **Intermediate** | 비즈니스 로직 (is_reverted, 3D 거리) | CREATE OR REPLACE (전체 재계산) |
| **Mart** | 분석 목적별 집계 | (분석 요건에 따라 정의) |

원본(Raw)은 어떤 경우에도 훼손하지 않는다. 파싱·계산 오류는 Staging/Intermediate 재실행으로 수정한다.

### 3. 역할 분리로 품질 확보

세 역할이 명확한 책임 범위를 가지며 순서 의존적으로 협업한다.

```
App Engineer  →  데이터 구조를 정의하고 구현
Data Engineer →  구조대로 수집·검증
QA/Tester     →  수집 트리거 역할 (로그 발생)
```

> QA/Tester의 역할은 앱 기능 검증이 아니라, **정의된 커맨드가 파이프라인에 도달할 수 있도록 로그를 발생시키는 것**이다.

### 4. 배포 순서 의존성

```
파이프라인 반영 완료  →  앱 배포  →  QA 수행  →  Spot Check
```

이 순서가 지켜지지 않으면 파이프라인 미반영 상태로 로그가 적재되어 분석 데이터에서 제외된다.

## 파이프라인 구조 개요

```
[Labelit 앱]
  커맨드 실행 시 CloudEvent 발행
       │
       ▼
[Zerobus / Kafka]
       │
       ▼
┌──────────────┐
│   Raw 레이어  │  CloudEvent 원본 JSON 보존
└──────────────┘
       │
       ▼
┌──────────────┐
│ Staging 레이어│  JSON 파싱, changes EXPLODE
└──────────────┘
       │
       ▼
┌──────────────────┐
│ Intermediate 레이어│  is_reverted 플래그, 3D 이동 거리 계산
└──────────────────┘
       │
       ▼
┌───────────────┐
│  Mart 레이어  │  분석 목적별 집계 (요건에 따라 확장)
└───────────────┘
       │
       ▼
[분석 / 대시보드]
```

## 검증 체계

로그 데이터를 자산으로 신뢰하기 위한 두 축의 검증이 상시 운영된다.

| 검증 | 시점 | 목적 |
|------|------|------|
| **Spot Check** | 신규 커맨드 등록 후 1회 | 정의된 커맨드가 Raw→Staging까지 도달했음을 확인 |
| **완전성 검증 (04a)** | 정기 배치마다 | Raw↔Staging 건수 정합, changes 배열 완전성, undo 시간 역전 등 |
| **품질 검증 (04b)** | 정기 배치마다 | NULL 규칙, 중복, orphan undo, position 구조 무결성 등 |
